# ADR 0001: Production architecture

Date: 2026-11-11. Status: accepted for Milestone 1; revisit items are marked.

## Context

The user selected a custom React/Electron desktop application and approved the visual design of the `prototypes/react-electron` experiment. Layout and typography of that design stand; its olive and amber colors were replaced on 2026-11-11, at the user's request, by neutral grays, cream, orange and a confirm green taken from the Factorio mod portal (tokens in `apps/renderer/src/styles/tokens.css`, rules pinned by `apps/renderer/test/themeColors.test.ts`). The handoff left the parser/runtime, diagram rendering, project format and build tooling as implementation decisions.

## Decisions

1. **Language implementation: hand-written TypeScript, no Java/Xtext.** A lossless tokenizer and recursive-descent parser keep every byte of source (trivia attached to tokens), produce diagnostics with ranges, a semantic `Circuit` and a source map. Graphical edits are pure functions from (parse result, command) to minimal text changes. Consequence: no JRE to ship, the language runs in the renderer, a worker and tests alike; we own completion/navigation ourselves. The prototype's source-preservation cases (comments, irregular spacing, rename, deletion, duplicate and reversed wires, stale drafts) are the acceptance proof in `packages/language/test`.
2. **Text is the persisted form and the single undo authority.** The CodeMirror document owns history. Layout lives in the source (`at (x, y)`), so a move is an ordinary undoable edit. Simulation state, traces and selection never create source edits.
3. **Identity.** Source identifies entities by name. The language session assigns stable ids that survive renames by matching declarations across parses; ids are not written to the file. Revisit when reusable components need cross-file instance identity.
4. **Module layout: npm workspaces.** `packages/model` (types), `packages/language`, `packages/catalog`, `packages/simulation`, later `packages/blueprints` and `packages/components`; `apps/desktop` (Electron main/preload) and `apps/renderer` (React workbench). Core packages have no React/Electron/Node dependencies. Packages are consumed as TypeScript sources and bundled with esbuild; `tsc` only typechecks.
5. **Rendering: custom SVG canvas, CodeMirror 6 editor.** No diagram library. Culling and memoization are added from measurements.
6. **Project format v1: a single file.** A project is one `*.faceproj` file: a standard zip archive, readable with any zip tool, with `face.json` (format version, name, game version, enabled module groups, custom signal groups and signals, circuit files, and optionally `wireReach`: how far apart two entities may be for a circuit wire in tiles, a number from 0 to 64 where 0 means unlimited, 9 when absent and then not written, a number out of range read as 0 or 64; still format version 1) and the `*.face` sources at the archive root. `assets/` is reserved for custom icons: tolerated and ignored on read, not written yet. Saving replaces the whole file atomically (temporary file in the same folder, fsync, rename). Reading treats the file as untrusted: size and entry-count limits, entry names checked, only the manifest and the circuits it lists are inflated; other root entries are ignored and not preserved on save. Runtime state is never persisted in it. A directory was the first choice and was replaced on 2026-11-11 at the user's request, before any release, so there is no reader or migration for it; the cost is that a project no longer diffs line by line in version control.
7. **Catalog: generated from the local game; icons read from the user's installation.** The generator runs the game's own data dump in an isolated write directory and records provenance. Catalog JSON is committed, and so is the icon table (`packages/catalog/data/icons-<version>.json`): for every icon id the image files of the game it is composited from, paths and numbers only. The images themselves are Wube artwork and are not part of the repository. The running app reads them from the game the user has installed (item 12) and composites each icon on demand with the same renderer the generator uses. A build may still carry rendered icons below its asset root (`packages/catalog/generated`, git-ignored, in development); they are the fallback when no installation is in use, and local builds only: redistribution rights must be resolved before a public release carries them.
8. **Simulation: deterministic two-phase tick engine** over indexed red/green networks, independent of the UI, publishing immutable snapshots. It will move to a worker when measurements require it; the API is already message-friendly (plain data).
9. **Security posture:** `contextIsolation` and sandbox on, Node integration off, restrictive CSP, a small validated IPC surface; the main process owns filesystem access and dialogs. Every IPC handler is registered through one function (`ipcHandle.ts`) that accepts calls only from the main frame of the app's own window at the app's own URL and answers with a result instead of rejecting. Two private schemes replace `file://`: `face-app://bundle/` serves the renderer bundle from one directory, `face-asset://catalog/` serves catalog icons. `face-asset://catalog/icons/<id>.png` is answered, in this order, with the icon rendered from the installation in use when the icon table has the id, with the file of that name below the asset root, with a placeholder drawn in code when the installation should have the icon but cannot provide it (a module that is not installed), and with 404 otherwise, on which the renderer shows names and pictograms. The renderer names an icon id and never a path; an id is only ever a key of the icon table, and the files the table names must really lie inside the installation's data directory (links resolved, regular `.png` files of bounded size, decoded with bounded dimensions and encoded again, so no file content reaches the page as it is).
10. **Containment during development:** `scripts/env.sh` redirects caches, temp files and app profiles into the repository; the app honours `FACE_USER_DATA` so development and test runs never touch the user's normal profile. `FACE_PROJECTS_DIR` sets the folder the open and save dialogs start in, so a development run can keep project files inside the repository too. `FACE_GAME_DIR` replaces the places auto-detection looks for the game with one folder; the end-to-end tests set it to a folder that does not exist, so no run uses a game that happens to be installed. `FACE_ASSET_ROOT` moves the asset root.
11. **Toolchain pins:** the versions proven by the prototype (React 19.3.1, Electron 44.9.1, TypeScript 6.0.3, esbuild 0.28.2, CodeMirror 6) plus vitest 5.1.0, Playwright 1.65.0, fflate 0.8.3, electron-builder 26.18.0. Upgrades (Electron 45, TypeScript 7) are deliberate later steps.
12. **The game installation is a setting of the application on this machine, not of a project.** It is stored in `app-settings.json` in the user-data directory (`{ version, gameDirectory }`; a missing or damaged file reads as the defaults). With nothing chosen the app looks for the game itself: the usual places of the platform (`/Applications/factorio.app` and `~/Applications` on macOS, the Steam libraries everywhere), each inspected by reading the `info.json` of the game's modules and checking for one image. A chosen folder may be the installation folder, its `data` directory or the macOS application bundle; when it holds no usable installation (any more) it stays chosen and its problem is shown, the app does not switch to another installation silently. An installation of another version than the catalog's is used all the same and the settings dialog says so (a note within the same minor release, a warning otherwise). The app only reads: it does not start the game and writes nothing into the installation. The search runs at start without holding up the window (the first icon requests wait for it, with a deadline, and a file system that stops answering costs a request two seconds, not the UI); icons rendered once are kept in memory and stay available when the folder goes away.
    The renderer reaches this through three calls without arguments and one event: read the state (chosen folder, data directory in use, source, game and catalog version and how they compare, modules present, problem, icon revision), open the native folder chooser, reset to auto-detection, and "the state changed". The folder comes from the chooser in the main process alone, so a compromised renderer cannot make the main process read a folder of its choosing: it can open the chooser (one at a time), reset the setting, read the installation's path and version, and fetch renders of the icon table's ids. Image URLs do not change with the installation; after a change at run time the renderer appends the icon revision as a query (`?r=<n>`, not for revision 0) so that images are fetched again.

## Open

- Asset redistribution (item 7; a packaged build no longer needs bundled icons, the packaging step has to stop copying them), packaging/signing targets, worker placement for parsing and simulation, shorthand for virtual signals in the language.
