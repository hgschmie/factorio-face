# ADR 0001: Production architecture

Date: 2026-11-11. Status: accepted for Milestone 1; revisit items are marked.

## Context

The user selected a custom React/Electron desktop application and approved the visual design of the `prototypes/react-electron` experiment. Layout and typography of that design stand; its olive and amber colors were replaced on 2026-11-11, at the user's request, by neutral grays, cream, orange and a confirm green taken from the Factorio mod portal (tokens in `apps/renderer/src/styles/tokens.css`, rules pinned by `apps/renderer/test/themeColors.test.ts`). The handoff left the parser/runtime, diagram rendering, project format and build tooling as implementation decisions.

## Decisions

1. **Language implementation: hand-written TypeScript, no Java/Xtext.** A lossless tokenizer and recursive-descent parser keep every byte of source (trivia attached to tokens), produce diagnostics with ranges, a semantic `Circuit` and a source map. Graphical edits are pure functions from (parse result, command) to minimal text changes. Consequence: no JRE to ship, the language runs in the renderer, a worker and tests alike; we own completion/navigation ourselves. The prototype's source-preservation cases (comments, irregular spacing, rename, deletion, duplicate and reversed wires, stale drafts) are the acceptance proof in `packages/language/test`. Since 2026-11-14, by the user's decision ("the entity definition should be the entity from the game"), an entity is declared by the game's name of its prototype, the one a blueprint has (`small-lamp light { ... }`, `"5d-lamp" l { }`), not by a keyword per family of behaviour with the prototype as a property: the language has no word for a kind, the kind of an entity (which decides how its block is read) is derived from the entity table in use, every entity of the model holds its prototype, and a name the data in use does not have is one error on the word. The earlier form is not read; no project of it existed outside the test data.
2. **Text is the persisted form and the single undo authority.** The CodeMirror document owns history. Layout lives in the source (`at (x, y)`), so a move is an ordinary undoable edit. Simulation state, traces and selection never create source edits.
3. **Identity.** Source identifies entities by name. The language session assigns stable ids that survive renames by matching declarations across parses; ids are not written to the file. Revisit when reusable components need cross-file instance identity.
4. **Module layout: npm workspaces.** `packages/model` (types), `packages/language`, `packages/catalog`, `packages/simulation`, `packages/blueprints` (since 2026-11-14: the blueprint string of the game, import of a blueprint as a circuit and export of a circuit as a blueprint; it uses the model, the language to make sure an imported circuit can be written exactly, and fflate; see its README), later `packages/components`; `apps/desktop` (Electron main/preload) and `apps/renderer` (React workbench). Core packages have no React/Electron/Node dependencies. Packages are consumed as TypeScript sources and bundled with esbuild; `tsc` only typechecks.
5. **Rendering: custom SVG canvas, CodeMirror 6 editor.** No diagram library. Culling and memoization are added from measurements.
6. **Project format v1: a single file.** A project is one `*.faceproj` file: a standard zip archive, readable with any zip tool, with `face.json` (format version, name, game version, enabled module groups, custom signal groups and signals, circuit files, and optionally `wireReach`: how far apart two entities may be for a circuit wire in tiles, a number from 0 to 64 where 0 means unlimited, 9 when absent and then not written, a number out of range read as 0 or 64; and optionally `gameMods`: the game the project was made with, item 15; both still format version 1) and the `*.face` sources at the archive root. `assets/` is reserved for custom icons: tolerated and ignored on read, not written yet. Saving replaces the whole file atomically (temporary file in the same folder, fsync, rename). Reading treats the file as untrusted: size and entry-count limits, entry names checked, only the manifest and the circuits it lists are inflated; other root entries are ignored and not preserved on save. Runtime state is never persisted in it. A new project is empty (one circuit without entities, not written anywhere until it is saved); the example of `docs/dsl.md` ships as a project file of its own (item 13). A directory was the first choice and was replaced on 2026-11-11 at the user's request, before any release, so there is no reader or migration for it; the cost is that a project no longer diffs line by line in version control.
7. **Catalog: generated from the local game; icons read from the user's installation.** The generator runs the game's own data dump in an isolated write directory and records provenance. Catalog JSON is committed, and so is the icon table (`packages/catalog/data/icons-<version>.json`): for every icon id the image files of the game it is composited from, paths and numbers only. The images themselves are Wube artwork and are not part of the repository. The running app reads them from the game the user has installed (item 12) and composites each icon on demand with the same renderer the generator uses. A build may still carry rendered icons below its asset root (`packages/catalog/generated`, git-ignored, in development); they are the fallback when no installation is in use, and local builds only: redistribution rights must be resolved before a public release carries them.
8. **Simulation: deterministic two-phase tick engine** over indexed red/green networks, independent of the UI, publishing immutable snapshots. It will move to a worker when measurements require it; the API is already message-friendly (plain data).
9. **Security posture:** `contextIsolation` and sandbox on, Node integration off, restrictive CSP, a small validated IPC surface; the main process owns filesystem access and dialogs. Every IPC handler is registered through one function (`ipcHandle.ts`) that accepts calls only from the main frame of the app's own window at the app's own URL and answers with a result instead of rejecting. The project calls are: `newProject()`, `openProject()` (native panel), `loadProject(path)` (an absolute, normalized path that ends in `.faceproj`), `openLastProject()` and `openExample(file)` (both item 13), `saveProject(request)`, `saveProjectAs(data)`, `getRecentProjects()`, `clearRecentProjects()` and `confirmUnsavedChanges()`; for blueprints of the game `importBlueprintFile()` and `exportBlueprintFile(request)` (item 14); beside them `paste()`, the three application-settings calls of item 12, the six game-data calls and their event of item 15, the dirty flag and the close handshake. Two private schemes replace `file://`: `face-app://bundle/` serves the renderer bundle from one directory, `face-asset://catalog/` serves catalog icons. `face-asset://catalog/icons/<id>.png` is answered, in this order, with the icon rendered from the installation in use (and, for data read from a game with mods, from the user's mods) when the icon table has the id, with the file of that name below the asset root, with a placeholder drawn in code when the installation should have the icon but cannot provide it (a module that is not installed), and with 404 otherwise, on which the renderer shows names and pictograms. An icon with an image of a mod among its layers that cannot be rendered is 404 at once: a mod that was removed or updated since the game was read, or an image the decoder does not read, shows as the name or the pictogram, never as a file of the same id that came with the build and never as the placeholder. The renderer names an icon id and never a path; an id is only ever a key of the icon table, and the files the table names must really lie inside the installation's data directory or, for a layer that names a file of a mod (`__<mod>__/<path>`, item 15), inside that mod (links resolved, regular `.png` files of bounded size, decoded with bounded dimensions and encoded again, so no file content reaches the page as it is). The main process shows one native context menu, for text (`contextMenu.ts`, a pure template like the application menu's): Copy where text of the page is selected, and Cut, Copy, Paste and Select All in a text field; nothing anywhere else, and where the page has a menu of its own (the canvas) it prevents the event. The items are role items, so they do what the Edit menu does through the page's clipboard events; no text of the page becomes a label and nothing crosses IPC.
10. **Containment during development:** `scripts/env.sh` redirects caches, temp files and app profiles into the repository; the app honours `FACE_USER_DATA` so development and test runs never touch the user's normal profile. `FACE_PROJECTS_DIR` sets the folder the open and save dialogs start in, so a development run can keep project files inside the repository too. `FACE_GAME_DIR` replaces the places auto-detection looks for the game with one folder; the end-to-end tests set it to a folder that does not exist, so no run uses a game that happens to be installed. `FACE_GAME_MODS_DIR` names the mod directory a game is read with (item 15) in place of the user's: with it the app looks at nothing of the user's own game files, the folder around it stands for the game's folder of the user's files, and the end-to-end tests set it to a folder that does not exist. `FACE_ASSET_ROOT` moves the asset root, `FACE_EXAMPLES_DIR` the directory of the example projects (item 13).
11. **Toolchain pins:** the versions proven by the prototype (React 19.3.1, Electron 44.9.1, TypeScript 6.0.3, esbuild 0.28.2, CodeMirror 6) plus vitest 5.1.0, Playwright 1.65.0, fflate 0.8.3, electron-builder 26.18.0. Upgrades (Electron 45, TypeScript 7) are deliberate later steps.
12. **The game installation is a setting of the application on this machine, not of a project.** It is stored in `app-settings.json` in the user-data directory (`{ version, gameDirectory }`; a missing or damaged file reads as the defaults). With nothing chosen the app looks for the game itself: the usual places of the platform (`/Applications/factorio.app` and `~/Applications` on macOS, the Steam libraries everywhere), each inspected by reading the `info.json` of the game's modules and checking for one image. A chosen folder may be the installation folder, its `data` directory or the macOS application bundle; when it holds no usable installation (any more) it stays chosen and its problem is shown, the app does not switch to another installation silently. The catalog it is compared with is the one in use: the built-in one, or the one read from a game (item 15). An installation of another version than the catalog's is used all the same and the settings dialog says so (a note within the same minor release, a warning otherwise). The app only reads here: it writes nothing into the installation, and it starts the game only when the user asks it to read the game's data (item 15). The search runs at start without holding up the window (the first icon requests wait for it, with a deadline, and a file system that stops answering costs a request two seconds, not the UI); icons rendered once are kept in memory and stay available when the folder goes away.
    The renderer reaches this through three calls without arguments and one event: read the state (chosen folder, data directory in use, source, game and catalog version and how they compare, modules present, problem, icon revision), open the native folder chooser, reset to auto-detection, and "the state changed". The folder comes from the chooser in the main process alone, so a compromised renderer cannot make the main process read a folder of its choosing: it can open the chooser (one at a time), reset the setting, read the installation's path and version, and fetch renders of the icon table's ids. Image URLs do not change with the installation; after a change at run time the renderer appends the icon revision as a query (`?r=<n>`, not for revision 0) so that images are fetched again.
13. **Start and examples.** A window starts with an empty, unsaved project and shows it at once. It then asks the main process for the project that was open last (`openLastProject()`, no arguments: the main process takes the top entry of the recent projects and reads it like any project) and shows that instead, without a prompt and without an unsaved change; the project is recorded as opened, as if it had been chosen from Open Recent. With no recent project the empty one stays. When the last project cannot be read (deleted, moved, damaged) the empty one stays too and the window says so where it reports other file errors; an older recent project never stands in for it, and the entry keeps its place in Open Recent, exactly as a recent project that fails to open by hand does (the volume it is on may only be missing for now). The consequence is accepted: the message returns at every start until another project is opened or saved or the list is cleared.
    Example projects are ordinary project files in one directory: `examples/` of the repository in development, `examples/` below the application's resources when packaged (the packaging step has to copy `examples/*.faceproj` there), `FACE_EXAMPLES_DIR` for tests. The main process lists that directory once per run (regular files with the project extension directly in it, no links, at most 64, each read as a project; one that cannot be read is logged and left out) and shows the projects by name under File > Open Example. Choosing one sends the renderer its file name, and `openExample(file)` answers with the project and no path: an unsaved copy, so Save asks for a location, the shipped file is never written and the recent projects do not get it. The argument is untrusted like every other: it must be a plain file name (a string of bounded length without a path separator of any platform, a colon, `..`, a leading dot or a control character, ending in `.faceproj`) and one of the names the main process listed itself; then the file is read with the limits and the validation of any project file. `examples/Feedback example.faceproj` is written by `npm run examples` (`tools/examples/generate.ts`, with the app's own project writer) from `tools/examples/Feedback example.face`, and a test fails when that source, the committed project file and the example of `docs/dsl.md` do not agree.
14. **Blueprints cross the process boundary as text; the main process only moves files.** Decoding, importing and exporting (`packages/blueprints`) run in the renderer, where a pasted string arrives anyway. The game has no blueprint files, so a blueprint file is ours: the blueprint string as the whole content of a text file, UTF-8 without a line break at the end, with the extension `.txt` unless the user names another one. Two calls, neither of which takes a path:
    `importBlueprintFile()` shows the native open panel (text and JSON files, or all files) and returns the name of the chosen file without its folders and its text: a regular file of at most 16 MiB (twice the longest string the importer reads; it refuses longer text unread), measured and read through one handle, decoded as UTF-8 or, with a byte order mark, UTF-16; anything else, also text with a NUL character, is "not a text file". Whether the text is a blueprint is for the importer to say.
    `exportBlueprintFile({ name, text })` validates first and then shows the native save panel. `text` must be a blueprint string and nothing else: a string of at most 8 MiB (the longest the importer reads back) that matches `0`, base64 characters and at most two `=`, so no blanks, no line breaks and no other content. `name` is the project name (the limits of a project name); the suggested file name is made from it by replacing everything outside `[A-Za-z0-9 ._-]`, so it can name neither a folder nor a hidden file. The file is written atomically like a project file (temporary file in the same folder, fsync, rename), and the call returns the path the user chose. One of the two panels is open at a time; a call made meanwhile answers like a cancelled panel.
    What a compromised renderer can do with them: open the two panels (one at a time); read, as text, a file of at most 16 MiB that the user picks in the open panel; and write a string of the character `0` and base64, of at most 8 MiB, to a place the user picks and confirms in the save panel. It cannot name a path, a folder or an extension, cannot write anything but that alphabet, and reads nothing the user did not choose. An imported blueprint becomes a project only in the renderer: it asks the main process for the empty project (`newProject()`, which also clears the window's file) and fills it, so it has no path, is not a recent project, and reaches the disk only through Save with the validation of every project.

15. **The entity and signal data can be read from the user's own game; the app runs the game for that, and only when asked.** The data that ships with the app (catalog, icon table, entity table of the standard game, item 7) is what a fresh installation works with. The settings of the application have an action that rebuilds the three tables from the installed game as the user has it, mods included. It never runs by itself: not at start, not when the game or its mods change (the dialog then only says that they did).
    *What is executed.* The program beside the `data` directory of the installation in use (`factorio.app/Contents/MacOS/factorio`, `bin/x64/factorio[.exe]`), links resolved, three times in a row and each time headless: `--dump-data`, `--dump-prototype-locale` and a scenario of the app (`tools/catalog/runtime-dump/control.lua`, bundled into the main script as text) that writes the finished prototypes. These are the three commands of the catalog generator (`tools/catalog/lib/commands.ts`), and the tables are built by its single-set mode (`tools/catalog/lib/single.ts`). The code of every mod the user has enabled runs in the game, as it does when they play. The folder comes only from the installation setting (item 12), that is from the native chooser or auto-detection; no call names a program.
    *The isolation.* No shell, fixed arguments, an environment of its own (nothing of the host's but `SystemRoot` on Windows), a private `config.ini` whose every writable path is in a fresh folder below `game-data-runs/` in the user-data directory, HOME and the temp directory redirected there, and a private mod directory: copies of the user's `mod-list.json` and `mod-settings.dat` (which the game rewrites) and links to the mods (which it only reads). On macOS the game is enclosed in the system's sandbox (`sandbox-exec`: no write outside the run's folder, no IP networking) when that can be entered; when it cannot the game runs without it and the outcome says so. Every step has a deadline (5 minutes, 12 in all), output is bounded (16 MiB; the last 32 KiB are kept, control characters removed), six of the user's files are compared before and after by size and time, the run can be cancelled, a run under way is stopped before the app quits, and the folder is removed afterwards (leftovers of a crash at the next run). Steam builds get the game's application id in the environment so that they do not restart through the client; whether that suffices is untested.
    *The confirmation.* Before every run the main process shows a native message box, a sheet of the window (`gameData/confirmation.ts`): the real path of the program, that it runs headless three times, that the code of the enabled mods runs in it and how many there are, where the mods are read from, that nothing is written to the game's folders, a note for a Steam installation, and what could not be read of the mods. Its default button is Cancel. The path that was shown is passed on as `confirmedExecutable`, and `readGameData` starts nothing else: an installation that changed between the question and the run is refused.
    *The cache.* What was read is one file, `game-data.json` in the user-data directory: the three tables, what the game says it had loaded (its modules and the mods with versions), when it was read, the notes of the build, and a key of the game's state (version, build, enabled mods with versions, hash of the mod settings). It is read at start before the window loads, as untrusted as any file: a size limit (128 MiB), `parseGameData` (the catalog's structure with limits on records, lists and text lengths, the icon table's own parser, the entity table's own parser with limits on count and name lengths, mod names and versions, the three tables of one game version), the key's id, and a check that the entity table has the ten prototypes the editor has kinds of its own for (`missingEditorPrototypes` of `@face/model`). A file that fails any of this is left where it is and not used: the built-in data applies, the title bar and the settings dialog say why, and "Use built-in data" removes it. The file has a format version (2 since the records name their mods, 3 since a recipe also names the mods of its ingredients and products, and an item those of the recipes that make it, 4 since the icon table has the icons of mods; `GAME_DATA_FILE_VERSION`). A file of an earlier version is not converted, since only the game can say what it lacks: it is treated the same way, with the request to read the game again in place of the reason. The same checks run on what a read produced before it is stored; a failed, cancelled or refused read leaves the data in use untouched.
    *Switching.* The main process keeps two things apart: the data the window has, and the data the cache holds. A window gets the cached data when it loads: at start, and when it is loaded again, which is how a read or a discard is applied (the main process switches its icon table and the catalog version of item 12 when the main frame starts to navigate). The page asks for its data (`getGameData()`) before it reads a circuit and installs it with `setEntityTable` and `setCatalog`; if it cannot after all, it falls back to the built-in data with a message. Before the window is loaded again the renderer asks about unsaved changes as it does before any project is replaced; when the user keeps the window the data waits (`pending`), the dialog says so and offers "Reload the window". After the reload the project that was open last comes back (item 13) and the settings dialog opens again with the outcome.
    *The calls.* Six, none with an argument, and one event: `getGameData()` (source, problem, loaded mods, catalog and entity table or null for the built-in data, and the ids of the icons of that data, built in or read: the keys of the icon table in use, which the cache file holds anyway; the renderer gives no other icon a URL, so a signal, group or entity whose icon the table lacks is shown by its name or pictogram and no request for it is made; an icon of a mod is in the table and is drawn when it is asked for, see "Icons of mods" below), `getGameDataStatus()` (the source in use, the source that waits, whether the game's state differs from the data's key as far as its files say, which starts nothing, why the game cannot be read, the problem of a damaged file, whether there is something to discard, the wired entities the data lacks, and the state of the request), `readGameData()` (opens the confirmation and runs; resolves when it has ended; while a request is under way it answers at once and opens nothing), `cancelGameDataRead()`, `discardGameData()` (refused during a run), `applyGameData()` (loads the window again, refused during a run; the page cannot navigate, itself included, so the main process does it) and the event "the request moved on". The request is `idle`, `confirming`, `running` (step 1 to 5 of prepare, data, locale, runtime, collect, with the time it began), `done` (warnings, seconds per step), `failed` (message, the end of the game's log, warnings) or `cancelled`; the last three stay until the next request. When the game ended with an error and its log blames a mod, the message names that mod first, by title, version and name ("The mod LTN - Logistic Train Network 3.5.0 (LogisticTrainNetwork) failed while the game started, and the game cannot be read with it enabled. The game ended with exit code 1"): `gameData/failedMod.ts` reads it from the last error line of the game's own in the log, in the three forms in which the game names a mod (not loaded, an error in a required file, a non-recoverable error in an event), and says nothing for any other log. The wired entities a read left out are part of the status and not of the request (`leftOut`: name, reason, what was found; of the data the cache holds, else of the data in use), so the window has them after a restart: `gameData/leftOut.ts` makes them from the notes of the build in the cache file, whose format did not change ("left out: <name>: <finding>", one note per finding). The notes are text made from what a game with mods said: a note of another form is listed whole, a finding whose words are not known is kept under the reason `other`, names and findings are cut to one line of bounded length and the list to 500 entries.
    *What a compromised renderer can do with them:* open the confirmation (one at a time; the user still has to agree, to the program of the installation the app found or the user chose), cancel a run, discard the data that was read, read the data and its source, and have its own window loaded again. It cannot name a program, a folder, a mod or an argument, cannot answer the confirmation, and gets no path beyond what the settings already show. What reaches it from a hostile game, mod, dump or cache file is data that passed the checks above, of bounded size, and it is only ever rendered as text or looked up: mod and prototype names, display names, the game's log and failure messages are text nodes and plain message-box text; an icon id is still only a key of the icon table, whose layers may name `.png` files inside the game's own modules (item 9) and `.png` files inside a mod the game had loaded, and nothing else: see "Icons of mods" below.
    *The build blocks the main process for about 0.1 s* for the standard game (reading and parsing 30 MB of `data.raw`, building and validating the tables; measured 96 ms with the real game, 2026-11-14), once per read, while the window only shows progress. It stays on the main thread; a worker is the step to take if large mod packs show otherwise.
    *One set, with the creator of every record.* One dump cannot say what a record would be with fewer mods, but the game says which mod created each prototype (`prototypes.get_history`, asked by the scenario): every signal, group, subgroup, quality and wired entity of such data has that mod as its `modules` (`core` counts as `base`; `tools/catalog/lib/single.ts` has the rules). Two kinds of record name more, since their creator makes them of another mod's things: a recipe also names the mods of its ingredients and products (the recycler has a recipe for every item of every mod), and an item the mods that every recipe of its creator for it needs (the barrel that `base` makes of a mod's fluid). Such a record is there with all of its mods on. The head of the catalog describes each loaded mod by its own `info.json`: title, and of its dependencies the hard ones that the game had loaded. The app reads that one file per mod from the user's mod directory after the run, from the folder or out of the archive, with a limit of 64 KiB: the archive is never loaded, a reader on the file handle (`gameData/zipEntry.ts`) takes the end record, the central directory and the one entry, and refuses whatever does not fit the file or its limits (200,000 entries, names of 1024 bytes, a directory of 32 MiB, stored and deflate only, no encryption, no archive in parts; zip64 is read). A mod whose `info.json` cannot be read is listed by its name without dependencies, and the outcome of the read says how many there are.
    *The project switches the mods.* The module list of a project (`modules` in `face.json`) has one meaning whatever data is in use: what is on. It is the game's own modules and, with data read from a game, the mods that a signal or a wired entity names as its creator; a mod that adds neither is counted in the project settings, not listed, and never written into a project. `base` is always on. A module switches on with what it requires, also through mods that are not listed, and off with what requires it (`listedModules` of `@face/catalog`). A new project has the game's own modules that the data has and no mod; a blueprint import adds the modules its signals and entities are of, with what they require, and its report names them. A signal or an entity of a module that is off stays in the source, is drawn, simulated and exported, gets a warning that names the module (`disabled-signal`, `disabled-prototype`, `docs/dsl.md`), and is not offered; the project settings say which such modules the project uses and switch them on with one button. A project saved while the list was fixed has no mod in it and opens that way, without a conversion. A group or a subgroup is there with something in it, whoever created it: the tags of the containers do not switch them. Accepted limit: one dump is one set, so what mods change in each other's prototypes stays as with all of them loaded, whatever a project has on.
    *The record in the project file.* `gameMods` in `face.json`: `{ "gameVersion": "2.1.24", "mods": [{ "name": "base", "version": "2.1.24" }, { "name": "some-mod", "version": "1.2.3" }] }`, what the game had loaded by its own account, its own modules first. It is written on save while the data in use was read from a game with at least one mod, and then replaces the record the project had; with any other data in use (the built-in one, a game without mods) the record is written back as it was read. It is validated like the rest of the manifest (three-number versions, names of at most 200 characters without control characters, each once, at most 2000 entries; fields inside it that this version does not know are dropped) and does not change the format version. A project opens whatever it says. On open the record is compared with the data in use, and a message names the mods (and modules of the game) the data lacks, the mods it has in another version, and a game version that differs; the project settings keep showing it. An entity of a mod the data lacks is an error in the source, as any unknown prototype is (`docs/dsl.md`), so its circuit is not drawn until the game is read with that mod; a signal the data lacks is a warning.
    *Icons of mods.* The icon table of such data keeps an icon whose layers name files of the loaded mods, in the notation of the game's own data: `__<mod>__/<path>`, where a name that is none of the game's own modules is a mod's (`modFileLocation` of `@face/catalog/icons`; the name as the list of loaded mods may have it, up to 100 characters, the path relative, ending in `.png`, no segment empty, beginning with a dot or holding a backslash, a colon or a control character, the whole within 300 characters). The table that comes with the build has no such layer and its generator refuses one. An icon is left out, and counted in a warning of the read, only when a layer cannot be named so: a file of a mod the game had not loaded, or a path of another form. The table does not say where a mod is. The icon service of the main process (`gameIcons/gameIcons.ts`, `modFiles.ts`) finds it when an icon is asked for, in the user's mod directory as it is then (`locateUserData`, or `FACE_GAME_MODS_DIR`): the folder or archive whose name and whose own `info.json` say that it is the mod in the version the game had loaded when the data was read (`GameData.mods`), as the read finds the mods' descriptions. From a folder it reads the file with links resolved on both sides, so the link that a mod under development is gets followed and nothing is read outside the folder it points to. From an archive it reads the entry `<the folder of the archive's info.json>/<path>` through the bounded zip reader: the central directory of an archive is read once into an index of its images (`ZipArchives` of `zipEntry.ts`; an archive is opened for each entry and closed again, at most eight files at a time; an archive that changed is indexed anew; the indexes are bounded to 256 archives and 48 MiB by an estimate and dropped with the data in use or the installation). Nothing is extracted or written. The limits are those of the game's own images: 1 MiB per file, a PNG of 8 bits per sample, not interlaced, at most 1024 pixels on a side. Whatever is not there or not that (the mod removed or updated, a file gone, an image of another form) is an icon without an answer, 404, and the renderer shows the name or the pictogram: `IconImage`, the status rows of the cards and the probes of the entity icons each give way on their own, and the first probe asks for three icons so that one mod's image cannot hide all the others. Measured with a real game of 44 mods (2026-11-17, 203 archives of 2.4 GB in the mod directory): 3591 icons in the table, 2730 of them with a file of one of 28 mods, 0 left out; 2727 are drawn, 3 are not (one image with 1 bit per sample); the first icon of a mod takes 1.7 ms on average and 6 ms at most (listing the mod directory once, finding the mod and indexing its archive), a further one 1.1 ms, where an icon of the game takes 0.9 ms; a hundred icons of mods asked for at once take 0.1 s and two hundred 0.17 s; the indexes of the 28 archives hold 0.6 MB by the estimate, and the archive with the most entries (1981, 51 MB) is indexed in 1.1 ms.
